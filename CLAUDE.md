# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with code in this repository.

## Команды

```bash
npm run dev        # vite dev server, порт 5173
npm run build      # tsc -b && vite build -> dist/
npm run lint       # oxlint
npm run preview    # раздать собранный dist (проверка прод-сборки)
```

Тестов в репозитории нет.

## Что это

Чистилка спрайтов: заделка дырок в обводке, сглаживание контура, чистка
цветовой ряби, пикселизация непиксельных ассетов. Всё считается **в браузере**,
серверной части нет — сборка деплоится как статика (Vercel определяет Vite сам).
Файлы пользователя никуда не загружаются, и это не деталь реализации, а
обещание в интерфейсе: не вводить сетевых вызовов с пользовательскими данными.

## Архитектура

Поток данных: `File` → `createImageBitmap` → `OffscreenCanvas` → `ImageData` →
пул воркеров → `Uint8ClampedArray` → холст превью и PNG-блоб для ZIP.

- `src/lib/pixelfix.ts` — всё ядро, чистые функции над типизированными
  массивами, без DOM. Единственная точка входа — `processImage(bitmap, settings)`.
- `src/worker.ts` — тонкая обёртка: принимает буфер, зовёт ядро, отдаёт результат.
- `src/pool.ts` — пул воркеров по числу ядер (максимум 4), очередь задач.
- `src/App.tsx` — состояние, инструменты, плавающие панели, ZIP.
- `src/EditorCanvas.tsx` — холст: зум, панорама, лассо, клики инструментов.
- `src/Toolbar.tsx` — вертикальный ряд инструментов и переключатели панелей.
- `src/FloatingPanel.tsx` — плавающее окно настроек, помнит своё место.
- `src/storage.ts` — сессия: localStorage для настроек, IndexedDB для файлов.

### Порядок шагов в `processImage`

Порядок не переставлять, каждый шаг опирается на результат предыдущего:
пикселизация → порог альфы → снятие обводки → внутренние полости → закрытие
щелей → правило соседей → despeckle → снятие светлой каймы → сглаживание
контура → слияние похожих цветов → палитра и сглаживание цветовых зон →
рисование обводки снаружи → перекраска кромки → defringe → бинаризация альфы
→ растяжка цвета за контур.

Когда размер пикселя задан, шаги после пикселизации идут **по маленькой
картинке**, где один пиксель равен одному арт-пикселю, а разворот в исходный
размер делается в самом конце. Иначе despeckle, defringe и сглаживание режут
куски мельче арт-пикселя, и на растянутом результате они видны как грязь по
краям блоков: на тестовом спрайте 48×48, растянутом в 8 раз, старый порядок
пачкал 249 блоков из 2304, новый — ни одного. Побочное следствие: все ползунки
с пикселями при включённой пикселизации считают арт-пиксели, а не экранные.

Отсюда основной сценарий («Обводка заново» в интерфейсе): снять старую
обводку целиком, восстановить тело заливкой от соседей, выровнять силуэт,
нарисовать обводку заново по чистому краю. Чинить рваную обводку на месте
бесполезно — её форма повторяет рваный силуэт.

Сценарий трогает **только контур**. Слияние оттенков и сглаживание зон в него
не входят: они работают по всей картинке и на мачете меняют 93% и 19%
внутренних пикселей соответственно. Для пиксель-арта это потеря рисунка,
поэтому такие шаги включаются вручную и осознанно.

Пикселизация идёт первой, потому что вся дальнейшая чистка должна работать уже
по новой сетке. Растяжка цвета — последней, потому что ей нужна финальная альфа.

### Приёмы, на которых держится качество

- **Заливка цвета — мода соседей, а не среднее.** `fillColors` расходится
  волной от известных пикселей и выбирает цвет голосованием, поэтому новых
  промежуточных оттенков не появляется. Замена на усреднение размоет пиксель-арт.
- **Палитра для голосования — не палитра для покраски.** Когда
  `paletteColors` равен нулю, `smoothRegions` голосует по авто-палитре из 32
  оттенков, но красит пиксель фактическим цветом ближайшего соседа из
  выигравшей зоны. Если красить цветом палитры, на богатом спрайте тридцати
  двух оттенков не хватает и цвета уезжают: фиолетовая кожа босса
  обесцвечивалась до серой (r−g падал с 40 до 20).
- **Голосование по палитре вместо работы с сырым цветом.** У картинки после
  масштабирования почти каждый пиксель уникален, голосовать не за что —
  поэтому `smoothRegions` и режим `pixelDominant` сначала строят палитру.
- **`regionKeep` защищает тонкие линии.** Пиксель меняет цвет, только если его
  оттенок слабее победителя в `(1 - keep)` раз. Без этого обводка в два пикселя
  проигрывает голосование заливке тела и растворяется.
- **Премультиплицированная альфа при уменьшении.** Иначе прозрачные пиксели
  подмешивают свой мусорный цвет в края.
- **`boxBlur` через интегральное изображение**, края продлеваются — иначе
  силуэт у рамки картинки подъедается.
- **Полости отбираются по толщине, а не по площади.** Артефакт — тонкая щель
  вдоль обводки: длинной она бывает, толстой нет. Настоящее отверстие
  переживает эрозию. На наборе из 30 ассетов это разделило 5946 артефактов
  (толщина 0–1, площадь до 197 px) и 14 настоящих отверстий (толщина ≥2,
  одно из них площадью всего 43 px). Отсюда `holeThickness`.
- **Снимается только тонкая лента у кромки.** `stripOutlineColor` ограничен
  глубиной `stripDepth` от края и морфологическим открытием: толстые области
  того же цвета (тёмные штаны, ботинки, волосы) переживают эрозию и остаются.
  Без открытия у персонажа сносило ноги целиком — тёмная одежда сливается с
  обводкой в одну связную область.
- **Новая обводка наращивается наружу** (`outlineGrow`), а не внутрь: иначе
  спрайт худел бы на толщину снятой каймы.
- **Цвет обводки берётся модой самых тёмных пикселей кромки, и на фотографии
  это подводит.** У фото обводки нет, и мода оказывается оттенком тела —
  обводка рисуется, но сливается с картинкой (на тестовом «фотоспрайте»
  находился цвет 155,87,90). Поэтому цвет задаётся и вручную: пипеткой по
  картинке или пикером в окне «Обводка», а «Авто» возвращает определение.
- **Наращивание и эрозия считаются двумя проходами, по строкам и столбцам.**
  Квадрат раскладывается на два отрезка, поэтому цена не зависит от радиуса.
  Повторение соседства радиус раз стоило на 2048×2048 две лишние секунды при
  радиусе 32 — а ползунки обводки доходят как раз до 32, потому что у
  пикселизованной картинки обводка в один арт-пиксель это целый блок.
- **Край обводки сглаживается отдельно от цвета.** `outlineSmooth` голосует
  по одной маске «обводка или нет», а не по палитре, поэтому выпрямляет
  границу обводки с заливкой, не трогая рисунок: на мачете это 44 изменённых
  пикселя в глубине против 4581 у сглаживания зон.
- **Обводка перерисовывается, а не чинится заливкой.** Заливка красит разрыв
  модой соседей, а вокруг разрыва соседей-заливки больше — обводка так и
  остаётся дырявой. Поэтому `outlineThickness` красит всю кромку найденным
  цветом обводки.
- **Порядок якорей в `mergeSimilar` и выборке тёмных в `detectOutlineColor`
  строго детерминирован** (частота, при равенстве — значение цвета), чтобы
  одинаковый вход всегда давал одинаковый результат.

### Определение размера арт-пикселя

`src/lib/detectPixelSize.ts`, кнопка «Определить размер» в окне «Пикселизация».
Отвечает на вопрос «это растянутый пиксель-арт, и если да, то с каким шагом и
откуда начинается сетка», и ставит найденное в `pixelBlock`, `pixelOffsetX`,
`pixelOffsetY`.

Считает по одной выбранной картинке: ползунки общие для пачки, но врать за
файлы, которых пользователь не видел, не стоит.

- **Решают перепады цвета, а не однородность блоков.** У настоящего спрайта
  половина площади — ровные заливки, и однородным там будет любой размер
  блока: проверка однородностью не находила сетку вовсе, зато уверенно
  находила несуществующую на градиенте. Поэтому строится профиль перепадов —
  для каждой границы столбцов и строк складывается величина изменения цвета.
  Однородность осталась вторым фильтром.
- **Величина перепада, а не число перепадов.** По числу событий шумная
  картинка неотличима от сетки: шум сжатия даёт перепады всюду. По величине
  отличима — на линии сетки цвет прыгает на сотню, шум ползает у порога.
- **Период ищется суммой Фурье, а не сравнением с допуском.** Для каждой
  пробной частоты считается, какая доля массы перепадов сидит ровно на ней.
  Ответ не зависит от допусков, работает с дробным шагом и заодно даёт фазу —
  начало сетки — точнее пикселя. Предыдущая версия сравнивала положения линий
  с допуском ±1 и на мелком дробном шаге ломалась: у кирки из `Pack 1` сетка
  3.53 px (145 арт-пикселей в 512) просто не проходила отбор, хотя видна
  глазом. Спектр показывает её с уверенностью 0.56.
- **Перебор идёт по частоте, а не по периоду.** Ширина пика в периоде растёт
  как квадрат периода: равномерный шаг по периоду либо промахивается мимо
  мелкой сетки, либо считает крупную сотню раз впустую.
- **Из кратных периодов берётся самый крупный, звучащий не слабее.** Половина
  настоящего блока звучит на той же гребёнке не тише целого — все линии сетки
  лежат и на половинных. Проверяются именно кратные пику периоды: правило
  «просто самый крупный из сильных» уводило на случайную низкую частоту — на
  портрете зомби с настоящих 5 px на 48.7.
- **Два порога перепада на одном проходе.** У картинок с плотным шумом
  (фотореалистичный рендер) мелкие перепады идут сплошняком и топят сетку: на
  портрете зомби мягкий порог даёт 0.20 на 2.44 px, строгий — 0.76 на
  настоящих 5 px. У мягко закрашенных наоборот. Оба профиля считаются за один
  проход по пикселям: второй проход по картинке 2500×2500 стоит полсекунды.
- **Оси сводятся средним геометрическим, а не минимумом.** Сетка обязана быть
  одна и та же по горизонтали и по вертикали, поэтому оценка должна падать,
  если ось молчит. Но минимум — слишком строго: у фасада дома почти вся деталь
  горизонтальная, вертикальных перепадов мало, и настоящая сетка получала
  оценку молчащей оси.
- **Кратные периоды проверяются от исходного пика, а не от принятого.** Иначе
  после повышения 2 → 4 следующая проверка уходит на 12, и настоящие 8 не
  проверяются вовсе.
- **Порог однородности блока — 40, а не 20.** У арта, сделанного нейросетью,
  арт-пиксель не плоский: внутри живёт шум и лёгкий градиент. Со строгим
  порогом проверка отсеивала сотню ассетов из двухсот, включая те, где спектр
  находил сетку уверенно (дача 5.02 при 0.41, церковь 3.0 при 0.30). При
  сорока настоящие ассеты дают 0.87–1.0, а шум и картинка с убитой сеткой —
  ноль, то есть фильтр по-прежнему работает.
- **Ответ бывает слабым, и об этом говорится.** У шума и у картинки с убитой
  сеткой выходит 0.14–0.33, поэтому ниже 0.2 ответа нет вовсе, а между 0.2 и
  `SURE_MAGNITUDE` (0.35) размер ставится с оговоркой «сетка слабая, проверь
  глазами». В эту полосу попадает, например, `mainhand_axe.png` — 3.66 px при
  уверенности 0.24, и глазами сетка там есть.
- **Фаза важна не меньше размера.** Растянутую картинку часто обрезают, и
  тогда первый арт-пиксель начинается не с нуля. Резать от нуля бессмысленно:
  каждая ячейка соберётся из половинок двух соседних арт-пикселей, и останется
  ровно та рябь, ради которой всё затевалось. На спрайте 32×32, растянутом в 8
  раз и обрезанном на 3,5 пикселя, свёртка без сдвига мажет 98% площади, со
  сдвигом — ноль.
- **Период подгоняется к круглому.** Сначала к целому (3.998 — это 4, иначе
  разница накопится по картинке в лишний пиксель), потом к целому числу
  арт-пикселей по стороне: у необрезанной картинки сетка обязана уложиться в
  ширину без остатка.
- **Размер блока бывает дробным.** Картинку из интернета редко растягивают
  целым числом: 16 px арта в 100 px картинки — это блок 6.25, а `bush_dead.png`
  из `Pack 1` — это 67 арт-пикселей в 512, то есть 7.64. Поэтому `pixelize`
  считает границы ячеек округлением вверх — как их и раскладывает растяжение
  ближайшим соседом. Ползунок дробный размер не покажет (шаг у него целый),
  обработка считает точно.
- **Проверка на «Pack 1», 200 файлов.** Сетка находится у 120: фоны 17/17,
  небо 4/4, оружие 21/22, интерфейс 39/50, окружение 39/62. Ещё 45 файлов —
  это `ui_elements_1x`, нарисованные в своём разрешении: сетки там нет и быть
  не должно. Промахи собраны в зданиях окружения — они нарисованы почти
  фотографически.
- **Блоки без сетки — отдельный случай.** Бывает арт, у которого блоки есть, а
  общей сетки нет: каждый «пиксель» стоит где придётся. Спектр на таком молчит
  (у `mainhand_anchor.png` из «Pack 1» вся полоса 2–12 px держится на 0.08, а
  максимум — мусорный пик на 41 px), хотя блоки видны глазами. Отвечать
  «сетки нет» тут бесполезно — человек её видит. Поэтому размер оценивается
  медианой длин ровных участков цвета (`estimateBlockSize`): на файлах с
  известной сеткой она попадает почти точно (3.53 → 3, 5.0 → 5, 5.72 → 5,
  7.64 → 7), и в статусе честно сказано, что сетка не ровная, а размер —
  типичный.
- **Когда блоков нет вовсе, кнопка всё равно что-то делает.** У части ассетов сетки
  действительно нет — картинка нарисована гладко, и «пиксельной» её делает
  только рваный контур. Но человек жмёт кнопку, чтобы привести картинку к
  пиксель-арту, а не услышать «нельзя», поэтому такая картинка сводится к 128
  арт-пикселям по длинной стороне — с прямой оговоркой, что это выбор по
  умолчанию, а не находка.
- **Серверный детектор pixels.rocks не портируется.** Там Canny и Хафа через
  OpenCV, и это отдельный сервис с загрузкой файла. Здесь сервера нет, и
  обещание «файлы никуда не уходят» дороже пары процентов точности. Взята
  идея клиентской детекции оттуда же.

### Ручные правки

`magicSelect` — «волшебная палочка»: заливка по связности и похожести цвета от
точки клика. Стирания живут в `App` как стопка мазков на ассет (индексы
пикселей), а не в `Settings`: они не должны попадать в ключ кэша результатов и
уходить в воркер как параметр. Применяются к декодированным пикселям перед
обработкой, поэтому переживают любую смену настроек.

Заливка идёт по связности, и обводка на спрайте связная: клик в неё уносит её
целиком по всему рисунку (на боссе это 83 тысячи пикселей). Поэтому есть
отмена последнего мазка и предупреждение, когда захвачено больше 15% силуэта.

Допуск держим низким (14): по замерам заливка почти не растёт до 24, а на 32
клик в обводку забирает уже 28% спрайта.

`removeBackground` — отдельный инструмент для картинок из интернета: заливка
внутрь от рамки по нескольким цветам сразу, взятым с самой рамки. Нескольким,
потому что «прозрачный» фон часто оказывается запечённой шахматкой из двух
оттенков: между её клетками расстояние 34.6, одним допуском её не взять, не
задев рисунок.

Обе заливки умеют добор края (`feather`): каждый следующий слой берётся с более
широким допуском. Без него на антиалиасной картинке остаётся светлая кайма —
1224 пикселя против одного с добором 2.

Замкнутые карманы фона (между рукой и телом, в петлях) заливкой от рамки не
достаются, поэтому `removeBackground` добирает их отдельно — но только когда
фон многоцветный и второй по частоте оттенок занимает в кармане не меньше
трети. Шахматка делит карман примерно поровну; у белка глаза или блика один
цвет доминирует, а прочие — единичные пиксели тени. Первая версия проверяла
только число оттенков и съедала глаза.

`fillPolygon` + инструмент «Вернуть лассо» — ручная страховка от таких
ошибок: обведённая область возвращается из оригинала. Правки поэтому хранятся
типизированной стопкой (`erase` / `restore`) и накатываются по порядку —
восстановление снимает пометку, поставленную более ранним стиранием.

`CompareViewer` перевписывает вид по `viewKey` (id ассета), а не по `before`:
стирание рисует новый объектный URL, и по нему зум сбрасывался бы после
каждого клика ластиком.

### Что общее, а что своё у каждой картинки

Настройки обработки (ползунки во всех окнах) — общие для всей пачки, они
применяются к каждому файлу. Правки — стирания палочкой, лассо, убранный фон —
свои у каждой картинки: они живут в `edits` по id ассета. Поэтому «Убрать фон
у всех» — не режим, а прогон одного действия по каждому файлу со своими
цветами фона.

### Сессия

`src/storage.ts`. Настройки и состояние инструментов — в localStorage (пара
килобайт JSON, поднимаются синхронно в инициализаторе `useState`). Файлы и
правки — в IndexedDB: в localStorage они не влезут (лимит около пяти
мегабайт), а IndexedDB хранит Blob и `Int32Array` без сериализации. Потолки —
300 файлов и 150 МБ, выше сессия просто не сохраняется, о чём говорится в
статусе.

Восстановление нельзя защищать гардом по ref: в StrictMode он глушит второй
монтаж, и сессия не поднимается вовсе. Отмена — через флаг `alive`, повторный
запуск безвреден. Сохранение правок ждёт флага `restored`, иначе пустая карта
затрёт то, что лежало в базе.

### Раскладка редактора

Сверху строка файлов и действий, слева тулбар, центр — один холст. Настройки
живут не в боковой колонке, а в плавающих окнах.

Тулбар делится надвое. Сверху инструменты холста (рука, палочка, лассо) —
выбор палочки или лассо открывает окно «Инструмент» с их ручками: допуск,
добор и «Убрать фон», который работает тем же допуском. Снизу — окна
обработки (Обводка, Чистка, Цвет, Пиксели) и список файлов: это не
инструменты, а параметры пайплайна, общие для всей пачки.

Пипетки в тулбаре нет: она нужна только для цвета обводки и потому живёт
кнопкой в окне «Обводка». Своего окна у неё тоже нет — курсор пипетки и
строка «кликни по обводке» говорят всё, а после взятия цвета режим сам
возвращается к руке. Инструмент, которому нужна табличка «это не то, что ты
думаешь», стоит не в том месте.
Показ оригинала — кнопка «Оригинал» с удержанием; для долгого разглядывания
есть режим «Сравнить»: два холста бок о бок с общим видом. Постоянной пары
холстов нет — место на экране нужно всегда, а сравнение только моментами.

Состав открытых окон и их места сохраняются, поэтому раскладка переживает
перезагрузку вместе с сессией.

Горячие клавиши: H рука, W палочка, L лассо, I пипетка (те же буквы в
русской раскладке), Esc возвращает к руке, пробел на удержание — временная
рука, O на удержание — оригинал, F вписать, 1 — сто процентов. Клавиши зума
живут в `EditorCanvas`, потому что вид холста — его состояние.

Ctrl/Cmd+Z отменяет, с Shift — возвращает. История одна на всё: и мазки
ластиком, и движения ползунков лежат в общей ленте `history`, отменённое
уходит в `future`. Разделять их нельзя — пользователь ждёт, что отменится
последнее сделанное, а не последнее сделанное определённого вида.

Движение одного ползунка рождает десятки изменений, поэтому подряд идущие
правки одних и тех же ключей склеиваются в один шаг (окно `COALESCE_MS`).
Пресет вроде «обводка заново» меняет сразу много ключей — это отдельный шаг,
он не склеивается с соседними и откатывается целиком.

В обработчике клавиш `event.target` проверяется через `instanceof
HTMLElement`: при событии от window у него нет `closest`.

### Курсоры и подсказки

`src/cursors.ts` — нарисованные SVG-курсоры в data-URI (пипетка, палочка,
лассо) с горячей точкой в том месте, куда инструмент реально ткнёт, и строка
помощи под панелью зума. Системного `crosshair` мало: инструменты ведут себя
не так, как одноимённые в фоторедакторах, и об этом надо говорить прямо —
палочка не кисть, пипетка берёт цвет обводки, а не кисти, лассо возвращает
оригинал, а не выделяет для копирования.

### Тонкости UI, которые легко сломать

- Пул воркеров создаётся лениво через `useState(() => new WorkerPool())`, а не
  в `useMemo` с cleanup: StrictMode монтирует дважды, и cleanup убивал бы
  воркеры насмерть.
- Результаты **не обнуляются** при смене настроек — предыдущий кадр держится на
  экране до готовности нового, иначе картинка мигает пустотой. Устаревший
  результат помечается сравнением `result.key` с сигнатурой настроек.
- `EditorCanvas` перевписывает вид только при смене `viewKey` или размера окна
  (`fitted` ref). Иначе зум сбрасывался бы после каждого движения ползунка и
  каждого клика ластиком.
- Колесо слушается через `addEventListener(..., { passive: false })`: React
  вешает пассивный обработчик, который не даёт отменить прокрутку страницы.
- Шахматка рисуется в экранных координатах, до трансформации холста, поэтому
  клетки не растут вместе с картинкой.
- Буферы уходят воркеру через transfer, поэтому в `pool.run` делается копия —
  исходник ещё нужен для превью «до».
